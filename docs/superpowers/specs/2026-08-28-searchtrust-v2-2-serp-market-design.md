# SearchTrust v2.2 SERP 市场采集设计

日期：2026-08-28

里程碑：V22-022

状态：已确认，待实施

## 1. 目标

实现 SearchTrust v2.2 的 SERP 市场采集能力：针对用户已经确认的 3—5 个查询，在同一个目标坐标、设备、语言和国家上下文中，采集 Google Maps、Local Pack 和自然搜索结果，形成可恢复、可审计且受成本硬上限保护的内部市场快照。

该里程碑只负责市场事实采集和标准化，不选择最终竞争对手，不铸造正式证据 ID，不生成 Finding、评分、Top Action 或完整报告结论。

## 2. 已确认范围

### 2.1 包含

- 3—5 个已确认、去重后的原始查询；
- 每份报告一个固定目标点；
- Google Maps 和普通 Google Search 两类请求；
- Maps、Local Pack 和 organic 三类标准化结果；
- 同一报告统一的设备、语言、国家和位置上下文；
- 查询、坐标、设备、语言、国家、时间和服务商搜索 ID 的采集审计；
- 每个查询最多两个逻辑搜索请求；
- 每份报告最多 10 个逻辑搜索请求；
- 现有 SerpAPI 多密钥轮换、冷却和安全日志能力的共享复用；
- 每个逻辑请求的检查点、中断恢复和重复执行保护；
- 服务商空结果、部分失败、限流和预算截断语义；
- 可供 V22-023 竞品聚合和 V22-031 证据注册使用的严格内部快照；
- 固定夹具、回归测试和冻结合同差异验证。

### 2.2 不包含

- Geo-grid、多坐标或半径网格采集；
- 搜索结果翻页；
- 自动改写、扩展或追加地域词到用户查询；
- 竞争对手聚合、排序、确认或网站采集，这些属于 V22-023；
- 正式 `evidence_id` 铸造，这属于 V22-031；
- 直接生成冻结报告 `MarketSnapshot` 中需要正式证据 ID 的结果；
- 新增公开同步 API；
- 启用完整 v2.2 生产分析管线；
- 使用真实付费 SerpAPI 请求执行自动化测试；
- 保存无限制完整服务商响应、原始 HTML 或任何 API 密钥。

## 3. 技术方向

采用“独立 V2.2 市场采集器 + 共享 SerpAPI 请求组件”的结构。

1. 从 v2.1 大型抓取模块中抽出小型共享 SerpAPI 请求组件；
2. v2.1 原有入口改为委托共享组件，保留原行为；
3. V2.2 使用独立市场模型、采集器和后台检查点阶段；
4. 每个查询固定规划一个 Maps 请求和一个 Google Search 请求；
5. 采集器只输出内部市场快照，后续里程碑分别负责竞品聚合和证据注册。

不选择 V2.2 直接导入 v2.1 `_serpapi_get` 的方案，因为这会让新里程碑依赖大型旧版抓取文件。不选择直接扩展 v2.1 抓取管线，因为 V2.2 的预算、检查点和证据边界会与旧版报告流程混合。

## 4. 架构和数据流

V22-022 作为持久后台任务中的独立阶段运行：

1. **输入冻结**：验证 3—5 个查询、目标市场、设备、语言和国家；
2. **目标点解析**：优先使用显式经纬度，否则调用一次免费 Locations API；
3. **请求规划**：每个查询生成一个 Maps 请求和一个 Google Search 请求；
4. **预算校验**：在发出请求前确认逻辑请求计划不超过 10；
5. **检查点执行**：按规范请求摘要复用已完成调用，只执行缺失调用；
6. **结果标准化**：分别解析 Maps、Local Pack 和 organic，不跨类型去重；
7. **完整性判断**：至少三个查询同时完成两类请求；
8. **快照封装**：输出版本化内部 `SerpMarketSnapshot` 和限制说明。

V22-022 交付可被未来真实 `V22JobExecutor` 调用的阶段适配器，但不替换生产 `UnavailableV22Executor`，也不改变 `V22_ANALYZE_ENABLED` 的安全默认值。

建议的实现边界为：

```text
app/integrations/serpapi.py
app/collectors/serp_market.py
app/collectors/serp_market_models.py
app/jobs_v22/serp_market_stage.py
```

具体文件拆分可以在实施计划中按现有约定细化，但共享请求、领域采集和持久阶段三层职责不得重新混合。

## 5. 输入和统一搜索上下文

### 5.1 查询

- 只接受冻结 `AnalyzeRequest` 中已经确认的 3—5 个查询；
- 仅清理首尾空白并执行不区分大小写的重复校验；
- 发给服务商的查询保持用户原文，不追加城市、服务词或 `near me`；
- 查询在快照中保持输入顺序；
- 每个查询的两类请求共享同一目标点和本地化上下文。

### 5.2 设备、语言和国家

- 同一份报告的所有查询使用同一设备、语言和国家；
- 默认设备为 `mobile`；
- 默认搜索语言为 `en`；
- 业务上下文已经提供冻结设备或语言时使用该值；
- 国家参数从目标市场 `country_code` 规范化得到；
- 不根据查询内容、服务商响应或中途结果自动切换上下文；
- 快照同时记录请求上下文和服务商响应中可验证的实际上下文，二者不一致时写入限制。

## 6. 单目标点解析

### 6.1 显式坐标

目标市场同时提供合法纬度和经度时直接使用：

- 纬度范围 `-90..90`；
- 经度范围 `-180..180`；
- 不再调用 Locations API；
- 规范地点文本仍保留用于展示，但不能覆盖显式坐标。

### 6.2 免费位置解析

没有显式坐标时，使用目标市场的邮编、城市、区域、国家和展示名构造一次 Locations API 查询：

- 每份报告最多一次外部位置解析；
- 位置解析免费，不计入 10 次付费搜索预算；
- 响应写入检查点并按规范目标市场摘要缓存；
- 先过滤国家代码不匹配结果；
- 再按邮编、城市、区域和规范名称的精确程度确定性排序；
- 唯一最高匹配必须提供 GPS 坐标；
- 没有合格结果或最高匹配仍歧义时，在付费请求前停止；
- 不允许退回服务商代理默认位置。

### 6.3 引擎参数

- Google Search 使用固定 `lat`、`lon`、`gl`、`hl` 和设备；
- Google Maps 使用同一中心点，`ll` 固定为 `@纬度,经度,14z`；
- 所有 Maps 查询使用相同 `14z` 视野；
- 不传分页参数，不执行下一页请求；
- 服务商文档明确说明位置不会保证所有 Maps 结果都落在目标范围内，因此结果只表示该目标点下的排名响应，不声称是半径内完整商家名录。

## 7. 请求预算和调用计划

### 7.1 逻辑请求预算

每个查询固定两个逻辑请求：

1. `google_maps`：提供 `maps` 结果；
2. `google`：同时提供 `local_pack` 和 `organic` 结果。

因此：

- 3 个查询计划 6 个逻辑请求；
- 4 个查询计划 8 个逻辑请求；
- 5 个查询计划 10 个逻辑请求；
- 报告硬上限为 10；
- 读取已有检查点不增加逻辑请求使用量；
- 同一规范请求的密钥故障切换仍属于同一个逻辑请求；
- 不允许用剩余预算做翻页、额外位置或补充查询。

### 7.2 实际尝试审计

逻辑预算和实际网络尝试分别记录：

- `logical_call_limit`：最大 10；
- `logical_calls_planned`：输入查询数乘以 2；
- `logical_calls_used`：至少发出过一次的唯一规范请求数；
- `provider_attempts`：包括密钥切换和暂时失败后的受控重试；
- `provider_attempt_limit`：每个逻辑请求最多 3 次，整份报告最多 30 次实际网络尝试；
- `checkpoint_hits`：直接复用完成结果的次数；
- `location_resolution_calls`：0 或 1，不计入付费搜索预算。

单个逻辑请求的实际网络尝试硬上限固定为 3，包括密钥切换和任务恢复后的暂时错误重试。没有配置三个可用密钥时仍保持最多 3 次，而不是按密钥数量额外扩张。该上限防止持久任务重启后无限重复不确定计费请求；检查点和尝试审计必须保证同一逻辑调用跨重启累计执行该限制。

## 8. 共享 SerpAPI 请求组件

共享组件负责：

- 读取主、次、第三密钥槽；
- 使用安全指纹识别密钥，不记录密钥正文；
- 优先使用当前健康密钥；
- 对认证、权限、配额和限流错误执行现有故障切换；
- 对失效密钥执行冷却；
- 区分无配置密钥、全部暂不可用、网络错误、请求错误和响应错误；
- 删除或拒绝任何可能在异常、日志或快照中暴露密钥的 URL；
- 返回结构化调用元数据，而不是把服务商任意错误正文传播到报告。

兼容性要求：

- v2.1 `_configured_serpapi_keys`、`_serpapi_get` 和 `SerpApiKeysUnavailable` 的现有调用语义必须保持；
- v2.2 预检 GBP 现有适配器不得因抽取而改变结果；
- 现有密钥轮换、冷却和脱敏测试先迁移或扩展，再修改调用方；
- 不得在 V2.2 采集器中复制第二套密钥轮换实现。

## 9. 内部数据合同

内部模型使用严格、版本化并拒绝额外字段的 Pydantic 合同。名称可以按项目约定细化，但必须覆盖以下语义。

### 9.1 `SerpTargetPoint`

- 请求地点文本；
- 规范地点名；
- 国家代码；
- 纬度和经度；
- 来源：`explicit_coordinates` 或 `serpapi_location`；
- 可选服务商位置 ID；
- 解析时间；
- 位置解析响应校验摘要；
- 不包含 API 密钥或带密钥 URL。

### 9.2 `SerpCallRecord`

- 稳定调用 ID 和规范请求摘要；
- 查询和引擎；
- 结果类型范围；
- 坐标、国家、语言、设备和可选 Maps 视野；
- 状态：`succeeded`、`failed_transient` 或 `failed_deterministic`；
- 开始和完成时间；
- 服务商搜索 ID；
- 响应校验摘要；
- 逻辑请求是否已使用、实际尝试次数和检查点命中状态；
- 标准化错误代码，不保存任意服务商错误正文。

### 9.3 `SerpMarketResultRecord`

- 稳定结果记录 ID；
- 查询；
- `result_type`：`maps`、`local_pack` 或 `organic`；
- 原始位置；
- 排名来源：服务商位置或响应顺序；
- 商家名或结果标题；
- 可选目标 URL 和规范域名；
- 可选地点 ID、data ID 或 CID；
- 可选地址、电话、类型、评分和评论数；
- 可选摘要；
- 服务商搜索 ID、调用 ID 和响应校验摘要；
- 采集时间和完整搜索上下文。

字段必须有长度、数量和数值范围上限。每类结果每个查询最多保留前 20 条；不足 20 条时保留服务商实际返回内容。

### 9.4 `SerpQueryRun`

- 原始查询和输入序号；
- Maps 调用记录；
- Google Search 调用记录；
- 三类结果列表；
- 是否为完整查询组；
- 查询级限制。

Maps 和 Google Search 均成功时才是完整查询组。服务商成功返回空列表仍算成功调用和完整查询组。

### 9.5 `SerpMarketSnapshot`

- 固定 schema version；
- 报告或任务关联标识；
- 开始和完成时间；
- 目标点；
- 统一设备、语言、国家和 Maps 视野；
- 3—5 个查询运行；
- 三类结果计数；
- 完整查询组数量；
- 逻辑预算和实际尝试审计；
- 全局限制。

快照成功条件为完整查询组不少于 3。输入有 4—5 个查询时，允许少数查询部分失败，但必须保留失败调用、已取得结果和限制。少于 3 个完整查询组时不封装成功快照，已完成检查点仍保留供后续重试。

## 10. 结果标准化

### 10.1 来源映射

- Google Maps 响应的本地结果映射为 `maps`；
- Google Search 响应的本地结果映射为 `local_pack`；
- Google Search 响应的自然结果映射为 `organic`；
- 未识别服务商区块不自动猜测类型，只形成计数型限制。

### 10.2 排名

- 优先使用服务商明确提供的正整数位置；
- 缺少位置但响应顺序明确时，以一开始的响应序号作为位置，并标记排名来源；
- 非法、重复或超出上限的位置按确定性规则保留或拒绝并记录限制；
- 不因为缺少评分、地址或 URL 而重新排序；
- 不对三类结果执行统一排名。

### 10.3 重复结果

- 采集层不跨查询去重；
- 不跨 Maps、Local Pack 和 organic 合并；
- 同一商家在多个查询或类型出现是 V22-023 的有效出现频率信号；
- 同一响应区块内只有完全相同的服务商结果标识和位置才视为重复记录；
- V22-023 才按地点标识、规范域名、名称和地址执行商家身份聚合。

### 10.4 稳定记录标识

结果记录 ID 由版本、规范调用摘要、结果类型、位置和稳定服务商身份字段生成 SHA-256 摘要。该 ID 只用于内部快照关联和未来证据注册，不冒充正式 `evidence_id`。

## 11. 检查点和中断恢复

### 11.1 检查点键

每个搜索调用的检查点键至少包含：

- 检查点 schema version；
- 引擎；
- 原始查询；
- 目标坐标；
- 国家、语言和设备；
- Maps 视野；
- 结果上限和分页状态。

键使用规范 JSON 摘要，不直接暴露完整查询或位置文本。任何影响结果的参数变化都必须产生不同检查点键。

### 11.2 检查点内容

- 只保存有界、验证后的标准化响应和必要服务商元数据；
- 保存校验摘要并在读取时重新验证严格模型；
- 损坏、版本不匹配或请求摘要不匹配的检查点作为确定性错误拒绝；
- 已成功调用不得因任务重启、SSE 重连或 worker 租约恢复而重复发起；
- 失败调用不写成成功检查点，重试仍受实际尝试硬上限约束。

检查点提供至少一次任务执行下的规范结果复用。并发重复 worker 的互斥仍由现有任务租约负责，不夸大为供应商层面的绝对 exactly-once。

## 12. 故障语义

### 12.1 确定性错误

- 查询数量或唯一性不合法；
- 国家、设备或语言不合法；
- 显式坐标不合法；
- 位置解析无结果、国家不匹配或最高结果歧义；
- 没有配置任何 SerpAPI 密钥；
- 规范请求本身非法；
- 检查点损坏或与请求不一致；
- 服务商响应持续不满足已知合同且无法安全标准化。

确定性错误使用稳定内部错误代码，不向用户暴露密钥、堆栈或任意服务商正文。

### 12.2 可重试错误

- 连接、读取或总超时；
- 服务商 5xx 或暂时不可用；
- 全部已配置密钥处于限流或冷却；
- 可恢复的服务商处理失败。

可重试错误只重试未完成逻辑调用，不能重跑已有成功检查点。实际尝试达到硬上限后转为查询级失败，并按至少三个完整查询组的门槛决定阶段结果。

### 12.3 空结果和部分结果

- 成功响应没有结果不是系统错误；
- 某一结果类型为空但其引擎调用成功时保持空列表；
- Maps 或 Google Search 其中一个失败时，该查询不是完整查询组；
- 已取得的另一侧结果仍保留，供审计和后续重试比较；
- 至少三个查询组完整时可以成功，但所有缺失项必须进入 `limitations`。

## 13. 证据和后续里程碑衔接

V22-022 不生成占位或伪造的正式证据 ID。

V22-031 将依据内部稳定记录 ID 建立 Evidence Ledger 记录，并把以下定位信息一并写入证据：

- 查询；
- 坐标和规范目标地点；
- 设备、语言和国家；
- 搜索引擎和结果类型；
- 搜索时间；
- 服务商搜索 ID；
- 结果位置和来源定位信息；
- 响应校验摘要、健康状态和限制。

只有取得正式证据 ID 后，转换器才能构造冻结报告 `SearchResult` 和 `MarketSnapshot`。映射必须由调用方提供稳定记录 ID 到证据 ID 的完整关联；缺失关联时拒绝生成最终结果，不使用占位字符串。

V22-023 消费内部市场快照，按出现频率、排名、业务相关性和稳定商家身份提出候选竞争对手。该阶段不得改变 V22-022 保存的原始排名或跨类型重复信号。

## 14. 安全、隐私和可观测性

- 日志记录任务 ID、调用 ID、引擎、查询摘要、密钥槽、安全指纹、耗时、状态和标准化错误类别；
- 默认不在结构化日志中记录完整查询、地址或坐标；
- API 密钥、带密钥请求 URL、响应链接和原始上游错误正文不得进入日志、异常、检查点或报告；
- 位置解析和搜索响应均设置连接、读取、总超时和最大响应字节数；
- JSON 深度、列表长度、字符串长度和结果数量必须受限；
- 指标至少覆盖逻辑调用数、实际尝试数、检查点命中、密钥切换、空结果、部分查询、完整查询组和错误类别；
- 不保存服务商原始 HTML；有调试需要时使用脱敏固定夹具，不落地生产响应。

## 15. 测试策略

### 15.1 合同和输入

- 3、4、5 查询通过，少于 3 或多于 5 拒绝；
- 不区分大小写重复查询拒绝；
- 原始查询词和顺序保持；
- 设备、语言、国家和坐标边界；
- 严格模型拒绝额外字段、超长字符串和超限列表。

### 15.2 位置

- 显式坐标不调用 Locations API；
- 无坐标时只调用一次免费解析；
- 国家过滤、邮编/城市精确匹配和确定性排序；
- 无结果、国家不匹配、歧义和缺少 GPS 坐标；
- 位置检查点复用和损坏拒绝。

### 15.3 请求和预算

- 3 个查询恰好规划 6 个逻辑请求；
- 5 个查询恰好规划 10 个逻辑请求；
- 任何输入和失败路径都不能超过 10 个逻辑请求；
- 不出现分页、额外位置或隐式补充查询；
- Maps 固定坐标和 `14z`；
- Google Search 固定坐标、国家、语言和设备；
- 检查点命中不产生新搜索请求；
- 实际尝试硬上限生效。

### 15.4 服务商和标准化

- 脱敏 Maps、Local Pack 和 organic 固定响应夹具；
- 位置字段存在和缺失的排名映射；
- 每类最多 20 条；
- 空结果成功；
- 非法条目有界拒绝并形成限制；
- 跨查询和跨类型重复结果保持；
- 稳定结果记录 ID 可重复生成；
- 不保存未知大字段和完整原始响应。

### 15.5 故障切换和安全

- 主、次、第三密钥顺序；
- 认证、权限、配额和限流故障切换；
- 网络错误不错误地轮换所有密钥；
- 冷却和恢复；
- 无密钥、全部暂不可用和服务商错误分类；
- 日志、异常和检查点中不出现任何密钥正文；
- v2.1 抓取和 v2.2 GBP 预检现有行为回归。

### 15.6 持久阶段

- 单个调用中断后只补做缺失调用；
- 完整检查点在任务重启后复用；
- 请求上下文变化导致新检查点键；
- 损坏检查点拒绝；
- 三个完整查询组成功；
- 两个或更少完整查询组保持不可进入后续阶段；
- 4—5 查询中的部分失败生成限制；
- 生产执行器和安全开关保持关闭。

### 15.7 全量验证

- V22-022 专项测试；
- 现有 v2.1 和 v2.2 全量 Python 测试；
- Python 编译检查；
- 冻结报告 schema 和类型导出差异检查；
- 工作树只包含计划内文件；
- 自动化测试不发出真实付费 SerpAPI 请求。

## 16. 验收标准

V22-022 完成时必须满足：

1. 3—5 个确认查询在同一目标点、设备、语言和国家上下文中执行；
2. 每个查询最多一个 Maps 和一个 Google Search 逻辑请求；
3. 每份报告逻辑搜索预算永远不超过 10；
4. Maps、Local Pack 和 organic 均可从固定夹具稳定标准化；
5. 每类每查询最多保留 20 条且不翻页；
6. 查询、坐标、设备、语言、国家和时间均可从内部快照追溯；
7. 至少三个查询组完整才能进入后续竞品阶段；
8. 中断恢复不会重复执行已成功调用；
9. 密钥轮换延续现有机制且无秘密泄漏；
10. V2.1 SerpAPI 调用和 V2.2 GBP 预检行为无回归；
11. 不生成伪造证据 ID；
12. 生产完整分析管线仍保持关闭；
13. 专项、全量和冻结合同验证全部通过。
