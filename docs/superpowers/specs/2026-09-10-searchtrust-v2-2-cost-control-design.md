# SearchTrust v2.2 成本控制设计

日期：2026-09-10

状态：设计已批准，尚未实施。

对应开发计划：V22-082 成本控制。

## 1. 目标

V22-082 为每个 V2.2 逻辑任务建立可恢复、可审计的内部成本账本，覆盖：

- Firecrawl 请求；
- Jina 请求；
- SerpAPI 请求；
- PageSpeed 请求；
- GSC、GA4 和官方 GBP 请求；
- Dify 调用、输入 Token、输出 Token 和总 Token；
- 总墙钟耗时、实际执行耗时、自动重试和检查点复用。

账本服务于内部运营、故障诊断和后续制定预算。它不向用户展示请求量、Token、单价、美元估算或供应商余额。

## 2. 已确认的业务决策

1. 记录真实调用量与 Token，并使用可配置单价估算美元成本。
2. 本阶段不设美元总成本目标、软上限或硬上限。
3. 美元估算不会中止任务、改变产品结果或减少已购买报告的内容。
4. 各供应商保留请求数或工作流调用数硬上限，用于防止并发与自动重试将一个逻辑任务放大成无界请求。
5. 同一逻辑任务的所有自动重试共用同一份账本和同一份硬上限。
6. 检查点命中不算新的供应商请求；真正发出的失败、超时、429 和 5xx 请求均计入真实尝试。
7. 不因“省成本”主动截断非核心深度。如果达到安全硬上限后仍无法完成产品承诺，任务失败并由 V22-080 现有终态机制返还一个 credit。
8. 用户重新生成时创建新任务、再次扣除一个 credit，并建立新的成本账本。
9. 报告继续显示真实的数据可用性和证据覆盖状态；它们不属于成本信息。报告不新增任何“成本预算覆盖率”。

## 3. 范围

### 3.1 范围内

- 付费 Prospect Report 和后续 Verified Report 任务；
- 报告前的竞品发现任务；
- GSC、GA4 和官方 GBP 同步任务；
- Redis 实时账本、终态汇总、回调同步和数据库持久化；
- 供应商价格版本与美元估算；
- 硬上限的原子申请、并发安全和跨重试共享；
- 内部运营可查询的任务汇总。

### 3.2 范围外

- 用户成本面板；
- 管理员可视化仪表盘；
- 基于美元金额的动态截断；
- 自动读取供应商账单或账户余额；
- 启用当前仍未进入 V2.2 主生成链的 Jina 或 PageSpeed 模块；
- 更改 V22-080 的计费、失败补偿或现金退款规则。

## 4. 架构

### 4.1 统一任务成本账本

新增 `JobCostLedger`，由任务 ID 唯一定位。它不是第二个任务状态机，不决定任务是否成功，只负责：

- 在外部请求前原子申请一个供应商尝试；
- 检查同一逻辑任务已用额度；
- 在请求完成后幂等记录结果、耗时和计费单位；
- 生成有界、可验证的扁平数字摘要；
- 在任务终态时将摘要写入持久数据库。

账本使用与任务相同的 Redis 前缀和 TTL。一个逻辑任务的 `run_generation` 变化不会创建新账本。

### 4.2 调用生命周期

每次可计费的外部请求有一个不含客户信息的随机 `claim_id`，并经历：

1. `claim(provider, operation, limit)`：在 Redis 中原子检查并占用一次额度；
2. 真正发出请求；
3. `complete(claim_id, outcome, duration, units)`：幂等补全结果。

如果进程在第 1 步后崩溃，该额度不会返还，并在汇总中记为 `outcome_unknown`。这是保守且符合真实计费风险的处理。

`claim` 之前的检查点命中、本地参数验证失败和熔断器本地拒绝不算供应商请求。它们可以分别记录为检查点命中或本地拒绝。

### 4.3 供应商适配边界

成本账本通过显式依赖注入或有界回调接入已有适配器，不在通用 HTTP 层根据 URL 猜测供应商。这保证：

- SerpAPI 的 Key 轮换尝试可以逐次计数；
- Firecrawl Map 与普通网站 HTTP 抓取不会混淆；
- Google 同步可以区分 GSC、GA4 和 GBP；
- Dify 可以在解析业务输出的同时解析 usage；
- 将来启用 Jina 或 PageSpeed 时，必须显式声明操作名与上限。

### 4.4 实时状态同步

`JobCostLedger.snapshot()` 输出 `CostCountersV1` 的扁平数字字典。报告 Worker 在以下边界把快照合并到现有 `JobState.cost_counters`：

- 进入 running；
- 准备自动重试；
- 成功终态；
- 失败终态。

现有签名回调将数字摘要持久化到 `analysis_jobs.cost_counters`。回调不接受字符串、嵌套对象、NaN 或无穷大。

## 5. 计数合同

### 5.1 通用字段

`CostCountersV1` 使用稳定的扁平键，所有值均为有限非负数字。至少包含：

- `cost_schema_version = 1`；
- `pricing_revision`；
- `job_wall_elapsed_ms`；
- `job_active_elapsed_ms`；
- `job_attempts`；
- `job_retry_count`；
- `provider_attempts_total`；
- `provider_successes_total`；
- `provider_failures_total`；
- `provider_outcome_unknown_total`；
- `provider_local_denials_total`；
- `checkpoint_hits_total`；
- `estimated_cost_usd_micros`；
- `pricing_unknown_units_total`。

每个供应商使用 `<provider>_<metric>` 命名，例如 `serpapi_attempts`、`firecrawl_duration_ms`、`dify_input_tokens` 和 `gsc_failures`。美元金额使用整数微美元，不使用浮点货币运算。

### 5.2 结果定义

- `success`：收到并通过该适配器最低响应边界的结果；
- `failure`：请求已发出，但出现网络、超时、429、5xx、4xx 或响应合同失败；
- `outcome_unknown`：已占用额度，但进程终止前未能持久化最终结果；
- `local_denial`：请求在发出前被硬上限或共享熔断器拒绝，不算供应商尝试。

请求失败也可能被供应商计费，因此 `failure` 和 `outcome_unknown` 都进入估算成本。

### 5.3 检查点定义

如果在请求前已获得完整、摘要匹配且通过合同验证的检查点，则：

- 增加对应阶段和全局的检查点命中数；
- 不申请供应商额度；
- 不增加供应商尝试、成功、失败或成本。

## 6. 硬上限政策

上限是产品和运行安全边界，不是美元预算。首版固定如下：

| 任务或服务 | 计数单位 | 单个逻辑任务上限 |
|---|---|---:|
| SerpAPI 市场/竞品发现 | 对任一 Key 真正发出的搜索尝试 | 30，另加 1 次地点解析 |
| SerpAPI 竞品公开 GBP/评论 | Place Details 或评论翻页尝试 | 15 |
| Firecrawl | 每个站点的 Map 请求 | 每站 1 次，一份报告最多 4 次 |
| Jina | 真实发出的请求 | 当前主链未启用，使用量必须为 0 |
| PageSpeed | 每个实际检测页面 | 启用时最多 5；当前主链为 0 |
| GSC | Search Analytics 请求 | 每次同步 12 |
| GA4 | Key Event 配置分页加报表请求 | 每次同步最多 28 |
| 官方 GBP | 资料、表现或关键词分页请求 | 每次同步最多 12 |
| Dify | Workflow 请求 | 每份报告最多 3 次尝试 |

SerpAPI 供应商尝试必须与现有每逻辑搜索最多 3 个 Key 尝试的限制同时满足。统一账本不能放宽更小的局部安全上限。

Dify Token 使用按响应中真实 usage 记录。单次 Token 限制继续由 Dify 工作流和其模型配置控制；后端不在无法预知真实 Token 时伪造事前精确限制。

## 7. 价格和美元估算

### 7.1 价格目录

价格目录是后端配置，包含：

- 数字 `pricing_revision`；
- 各供应商的每请求微美元；
- 如有必要，按供应商计费单位的微美元；
- Dify 输入和输出每百万 Token 的微美元。

所有价格配置都不是 secret，但只在后端使用。它们不注入前端构建。

### 7.2 未知价格

单价为空或无效时，对应的真实数量照常保存，并增加 `pricing_unknown_units_total`。未知单价不得默认解释为零成本。

如果 Dify 响应不包含可验证的 usage，记录 `dify_usage_unknown_calls`，不根据文本长度伪造精确 Token。

### 7.3 历史不重算

终态汇总保存当时的 `pricing_revision` 和估算微美元。价格调整只影响之后的新任务，不改写历史任务。

## 8. 持久数据

### 8.1 `job_cost_summaries`

新增仅 `service_role` 可读写的内部汇总表，字段包含：

- `job_id` 主键；
- `case_id`；
- `job_kind`: `competitor_discovery`、`prospect_report`、`verified_report`、`gsc_sync`、`ga4_sync` 或 `gbp_sync`；
- `status`: `succeeded` 或 `failed`；
- `attempt_count`；
- `cost_counters jsonb`；
- `started_at`、`completed_at`、`created_at` 和 `updated_at`。

`job_id` 冲突使用终态幂等 upsert，只允许相同任务更新为更完整的摘要，不允许修改 `case_id` 或 `job_kind`。

表启用 RLS，撤销 `anon` 和 `authenticated` 的所有权限，只授权 `service_role`。不提供浏览器 RPC。

### 8.2 现有任务表

- 报告任务继续在 `analysis_jobs.cost_counters` 保存同一摘要；
- `google_sync_jobs` 新增 `cost_counters jsonb not null default '{}'`；
- 竞品发现状态在 Redis 中保留运行摘要，终态摘要另外写入 `job_cost_summaries`。

正式报告汇总会引用已确认的竞品发现 ID，并将对应发现成本汇入报告级的端到端数字键。竞品发现自身的独立汇总仍保留，便于计算未进入付费流程的获客成本。

## 9. 与报告和前端的边界

- `ReportV22` 公开合同不新增成本字段；
- 任务公开状态不展示 `cost_counters`；
- 客户报告、分享报告和 PDF 不包含任何成本信息；
- 已有 `data_coverage`、数据源健康、身份匹配和证据 limitation 继续如实展示；
- 不创建“成本不足”、“预算裁剪”或“省略深度”类用户文案。

## 10. 超限、失败和恢复

### 10.1 超限处理

硬上限达到后，账本在发出下一个请求前拒绝额度。

- 若该供应商只是允许失败的补充发现手段，且已有证据足以完成现有报告合同，按现有数据覆盖规则继续；
- 若完成核心报告合同仍需要该请求，抛出固定安全错误，任务进入失败终态；
- 错误响应不暴露供应商额度、余额、单价或内部尝试数。

### 10.2 记账故障

在无法完成 `claim` 时不得发出外部请求。这是 fail-closed 边界，防止实际成本脱离账本。

如果外部请求已经发出，但 `complete` 暂时失败，预先写入的 claim 仍然占用额度。后续重试可幂等补全；无法补全时最终按 `outcome_unknown` 汇总。

### 10.3 与 V22-080 的边界

成本账本不直接修改 credit、Case entitlement 或支付订单。它只向现有任务状态机返回成功或安全错误。任务终态之后，V22-080 的数据库事务继续唯一决定消耗还是返还 credit。

## 11. 安全与隐私

账本和成本汇总不得保存：

- API Key、OAuth Token、Cookie、签名或密钥指纹；
- 客户邮箱、电话、商家地址或完整网址；
- 搜索词、Google 资源 ID、请求正文或原始响应；
- 供应商原始错误正文；
- Dify 的 prompt、工作流输入或生成文本。

允许保存的识别信息只有内部 job ID、Case ID、任务类型、固定 provider/operation 名和有界数字摘要。应用日志只输出 job ID 后缀、固定错误码和必要计数，不输出成本账本全文。

## 12. 测试策略

### 12.1 单元测试

- 计数模型拒绝负数、非有限数、未知键污染和过大摘要；
- 价格目录使用整数算术，Token 比例计算可重现；
- Dify usage 有值、缺失、非法和过大时均有安全处理；
- 不同 provider/operation 使用各自硬上限。

### 12.2 Redis 并发与恢复测试

- 超过上限的并发 claim 中只有有界数量成功；
- 重复 complete 不会重复增加成功、失败、耗时、Token 或成本；
- 重启、`run_generation` 变更和三次自动重试共用同一额度；
- 占用后未完成的 claim 在终态汇总中是 `outcome_unknown`；
- 账本 TTL 和任务状态 TTL 一致。

### 12.3 供应商适配测试

- 检查点命中不增加真实请求；
- SerpAPI Key 轮换对每个实际 Key 尝试计数；
- Firecrawl 对每站最多发出一次 Map；
- 429、5xx、4xx、网络错误和超时都记录失败尝试；
- 熔断器在请求发出前拒绝时不记 provider attempt；
- GSC 最多 12、GA4 最多 28、GBP 最多 12 次；
- Dify 最多 3 次，并正确记录 usage 或 usage unknown。

### 12.4 持久化与权限测试

- 成功、失败、竞品发现后放弃和 Google 同步均产生长期汇总；
- 回调重放和乱序不会回滚或重复成本；
- `anon` 和 `authenticated` 无法查询、插入、修改或删除内部成本表；
- `service_role` 可以幂等 upsert 汇总；
- 成本字段不出现在报告、分享报告、PDF 和公开任务响应中。

### 12.5 财务终态回归

- 成功任务保留一次扣费；
- 最终失败只返还一个 credit；
- 重复失败回调不重复返还；
- 用户再次生成创建新任务和新账本；
- 成本记账失败不会越权修改 credit。

## 13. 部署和运营顺序

1. 添加数据库迁移、RLS 和数据库合同测试；
2. 部署数据库迁移；
3. 部署后端成本模型、Redis 账本和供应商适配；
4. 验证回调可以向旧数据库字段写入扁平数字摘要；
5. 为当前价格目录配置 `pricing_revision` 和已知单价，未知项保持显式 unknown；
6. 运行后端、前端、数据库合同和安全权限全套测试；
7. 按先 API、后 Worker 的顺序发布后端；
8. 验证 API 健康、Redis/Worker 健康、回调积压和数据库权限；
9. 使用合成任务验证成功、失败、重试和检查点路径，不使用真实客户数据；
10. 确认未改变 Google 与 Verified Generation 现有功能开关。

数据库必须先于依赖新字段或新表的代码发布。

## 14. 验收标准

V22-082 只有在以下条件全部满足时才能完成：

1. 每个报告、竞品发现和 Google 同步任务都有唯一成本账本；
2. 所有实际外部尝试，包括失败与结果未知，都被保守计数；
3. 检查点命中不会重复增加供应商成本；
4. 并发和三次自动重试不能超过固定硬上限；
5. Dify 真实 usage 被记录，缺失 usage 时不伪造 Token；
6. 价格未配置时使用量仍然完整，且未知单位不被误报为零成本；
7. 终态汇总保存到 service-role-only 数据库边界；
8. 用户、分享访客和浏览器构建均无法访问成本数据；
9. 达到硬上限且核心产品合同无法完成时，任务失败并且只返还一个 credit；
10. 报告不显示成本、预算或供应商余额，同时保留真实数据覆盖说明；
11. 全套自动化测试、数据库权限测试和正式环境健康检查通过。

## 15. 原计划调整

V22-082 开发计划原文要求“超过预算时按明确顺序截断非核心深度，不影响已承诺模块，且报告显示 coverage”。

经本轮确认，该规则调整为：

- 首先获取生产真实调用量和估算成本；
- 不设美元预算，不为省成本交付缩水报告；
- 保留有界供应商尝试，用于防止运行放大；
- 核心合同无法完成时失败并返还 credit；
- 仅保留报告原有的真实数据覆盖说明，不展示成本或预算截断信息。

本设计文档是 V22-082 实施和验收的最新决策依据。
