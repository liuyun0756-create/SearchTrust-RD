# SearchTrust v2.2 证据索引设计

日期：2026-08-30

范围：V22-031

状态：用户已确认范围、独立适配层方案及核心规则；本书面设计待审核，尚未实施。

主要实施仓库：`SearchTrust-RD`。前端 `search-trust` 参与合同兼容性验证，不新增 UI。

## 1. 目标与非目标

将已取得的站点、SERP 市场、竞品及 GSC/GBP/GA4 快照转换为冻结合同中的 `EvidenceItem`，提供确定性的编号、来源定位、来源健康状态与限制说明，供后续 Findings 使用。

本轮交付可独立调用、离线运行的索引构建器及快照适配器，不交付完整报告生成管线。保留 v2.1 提取逻辑和行为，不修改报告/API 模型、Schema、合同版本 `2.2.0`、原始合法 fixtures 或生成的 TypeScript 类型。

不新增 OAuth、主动同步、外部采集、数据库迁移或快照写入服务。不实现 V22-032 Findings、V22-033 Actions、报告文案、报告 UI、PDF 或 PageSpeed 适配器。不启用两个 v2.2 生产开关，不替换 `UnavailableV22Executor`，不推送或部署。

## 2. 已核实的基础与方案选择

### 2.1 现有基础

- `app/report_v21/evidence_ledger.py` 提供页面文本、公开 GBP、评论和 schema 的提取能力；页面编号采用 `page-0001` 等顺序编号。已复现：前面插入一段文字会改变后续编号，不能直接用作 v2.2 证据身份。
- `SiteInventorySnapshot`、`SerpMarketSnapshot`、`CompetitorCollectionSnapshot` 已包含结构化采集结果，但并非都具有可用于报告引用的统一快照 UUID。任务 ID 不是快照 ID。
- `FirstPartySnapshotEnvelope` 已包含快照 UUID、健康及身份匹配状态、规范化行数据、来源请求上下文和校验和。
- 冻结 `EvidenceItem` 已要求 `snapshot_id`、标量原始值/规范化值及来源定位；不允许为实现方便新增任意字段。
- V22-030 已建立严格模型与前端校验一致性回归。前一轮核查的旧版证据质量、可读性及新版合同相关测试共 24 项通过；这不是本功能已完成的证明。

### 2.2 采用方案

新增独立 v2.2 适配层，复用旧版提取能力，但由新版索引核心拥有编号、去重与溯源规则。

未采用直接修改旧版 ledger 的方式，以免改变历史报告和规则绑定；也不完全重写提取器，避免重复已有文本清理能力。只调用旧版提取入口，不调用会生成规则结论的 `build_layer_evidence`。

## 3. 模块边界与数据流

拟新增以下后端模块，均不改变对外合同：

- `app/report_v22/evidence_models.py`：严格的内部构建上下文、快照绑定、来源追踪、覆盖缺口和输出模型。
- `app/report_v22/evidence_identity.py`：标量规范化、确定性身份和冲突检测辅助函数。
- `app/report_v22/evidence_adapters/`：分别拥有 site、serp、competitor、first-party 的字段选择与映射。
- `app/report_v22/evidence.py`：单一构建入口，验证全部来源、调用适配器、合并去重、排序并返回结果。

数据流为：调用方提供已加载的快照与绑定信息 → 验证来源归属/校验和 → 各来源提取观察值 → 统一编号与去重 → 返回证据及来源追踪、覆盖缺口。

输入上下文包括 `case_id`、报告类型、客户站点身份、目标市场、查询、有效搜索语言/设备、已确认竞品，以及调用方固定的 `evaluated_at`。可从现有 `AnalyzeRequest` 及采集器当前使用的搜索上下文派生，不把新的内部字段加入 Analyze API。市场未显式提供坐标时核对请求地区与国家，保留采集器解析后的真实坐标，不自行重新地理编码。

构建入口不得联网、读取数据库、修改原快照或直接提交 checkpoint；不得调用 LLM。快照加载与持久化属于调用方职责，本轮不接入生产 executor。

## 4. 快照绑定与信任边界

### 4.1 必需绑定

每个实际来源必须具有内部 `SnapshotBinding`，记录真实 `snapshot_id`、当前 `case_id`、来源类型、格式版本、载荷校验和、获取时间及已有的过期时间。第一方来源还需与 envelope 中的身份匹配/健康信息一致。

快照 UUID 由已加载快照的调用方提供：

- 第一方快照保留 envelope 的 UUID，不重算、不替换。
- 已有共享市场快照保留其 UUID；共享快照归属授权必须由调用方完成，不能因为来源任务不同就改造新 UUID。
- 没有自身 UUID 的站点/竞品采集结果，必须先由调用方提供真实快照记录的绑定，才能生成正式 Evidence。本构建器不以 job ID 冒充 snapshot ID，也不随机生成 UUID。
- 测试使用显式 fixture UUID 和相应内容校验和，只代表测试来源，不宣称已写入线上 `data_snapshots`。

绑定属于可信应用边界，不是客户端可自由提交的认证凭据。本地核对 case、来源和内容不等于数据库所有权授权；正式管线接入时，调用方仍须负责租户授权及真实记录存在性。

### 4.2 内容与归属验证

- 公开采集快照：对完整、经对应 Pydantic 模型验证后以 JSON 模式导出的载荷，使用现有稳定 JSON 序列化与 SHA-256 核对绑定校验和。
- 第一方 envelope 的 `payload_checksum` 对应 `normalized_payload`；同时核对绑定与 envelope 的 UUID、来源、获取时间、过期信息。不得拿整个 envelope 的哈希误比 normalized payload 的哈希。
- 同一次构建中，一个快照 UUID 只能对应一种来源、载荷校验和及一致的绑定元数据；发现冲突立即拒绝整个构建。
- UUID 注册表还比较完整已验证来源对象，包含第一方请求上下文和健康字段；不能因两个 envelope 的 normalized payload 相同就接受同 UUID 下不同的来源元数据。
- 客户站点根身份必须匹配；市场上下文必须匹配确认的查询、地区、语言/设备；竞品身份必须来自确认列表，竞品站点归属按现有域名规范化规则核对。共享市场来源任务可以不同，但其确认上下文不可不同。
- 校验有限数值、真实日期及覆盖期顺序。NaN/Infinity 必须在 JSON 编码前拒绝，不能让编码器将其变为 null。

公开载荷整体校验和与上游原始响应校验和不是同一种校验。比如页面 `content_checksum` 对应原始 HTTP 字节，不能通过重新编码已解码 HTML 假装验证原响应。本轮验证持有的规范化快照，保留上游摘要用于追踪；不在缺少原始字节时声称完成原响应复核。

## 5. 输出与来源定位

内部 `EvidenceBuildResult` 包含：

- `evidence_index`：按证据 ID 排序的 `EvidenceItem` 列表。
- `source_traces`：每条证据对应的快照引用、稳定记录选择器、原始字段路径，以及存在时的竞品 ID、指标单位和行维度。
- `source_summaries`：每个绑定来源的健康、身份匹配、使用资格、观察计数及完整限制清单。
- `coverage_gaps`：无快照、不可用、空数据、部分覆盖等确定性的结构化缺口。

只有 `evidence_index` 进入现有报告字段。其余为后续组装器内部输入，不擅自写入报告根节点，也不暗中改变 `SourceLocator`。

`SourceLocator` 优先保留 URL、外部 Property/Location 标识、query、坐标、设备和语言；`field_path` 使用有界、稳定的字段选择器。完整维度或定位内容太长时，使用其规范化摘要构成选择器，并在内部 trace 保留完整映射，不能截断后把不同来源合并。

数组行号只能作为追踪当前不可变快照的物理路径，不用于取代逻辑身份。每条证据至少能通过快照 UUID、稳定选择器和 trace 找回其来源。重复观察可对应多个物理路径，路径列表去重并排序。

本轮允许输出空证据列表及明确缺口，不填造 Evidence 或生成占位报告。完整报告要求非空索引的约束仍由后续报告组装阶段遵守。

## 6. 各来源的映射

| 来源 | 提取范围 | 身份与追踪要点 |
| --- | --- | --- |
| 客户站点 | 检查状态/HTTP 信息、title、h1、canonical、meta robots、schema types、页面类型、深度页可读文本片段及实际统计 | 根站点绑定、页面 URL、稳定字段或片段选择器；源类型为 site |
| SERP | 各 query 的 maps/local_pack/organic 结果位置、显示名称、URL、公开评分/评论数，以及实际调用状态与结果计数 | record/call 标识、结果类型、query、坐标、语言/设备；源类型为 serp |
| 竞品 | 已确认竞品的站点证据、公开 GBP 字段、实际评论及商家回复、出现场次与最佳位置 | 所有逻辑选择器绑定 competitor ID；源类型为 competitor，不冒充客户第一方 gbp |
| GSC/GBP/GA4 | 健康、身份匹配通过且未过期快照内已有的 aggregate/row 指标 | 外部资源 ID、指标 key、unit、完整行维度、覆盖期；不再计算或补造指标 |

### 6.1 页面复用边界

深度页通过旧版 `build_evidence_ledger` 的页面提取入口获得清理后的片段；每页单独构建最小上下文，不注入其他来源或规则结果。旧版 page 编号仅可作本次提取追踪，不能进入新版证据 ID。

旧提取器的片段数量与长度限制继续生效，触及限额时加入固定限制说明。不能把受限片段描述成完整页面，也不能凭没有提取到某词判定业务能力不存在。只处理结构检查而没有深度文本的页面，不生成正文内容证据。

### 6.2 标量与复杂字段

保持 `original_value` 和 `normalized_value` 为合同支持的标量。列表字段按实际元素生成观察；第一方每个指标单独生成观察，其完整维度和单位保存在 trace 并参与身份。禁止将整个 provider JSON 或整行数据塞入 JSON 字符串伪装标量。

`original_value` 为按现有合同验证后的提取标量，不承诺逐字节复制原始响应；完整来源以绑定快照及字段追踪为准。零值是实际测量值时保留，缺失不能转换为 0。

第一方上下文支持 `tablet`，而冻结 `SourceLocator.device` 只支持 desktop/mobile：tablet 保留在完整维度/上下文 trace，并参与选择器身份，报告 locator.device 留空且附限制说明，不改写成 mobile，也不扩大枚举。不能无证据地补入缺失的 query、坐标或语言。

## 7. 稳定 ID、去重与冲突

证据 ID 格式为 `ev_` 加完整 64 位小写 SHA-256 十六进制摘要，符合现有正则。

哈希输入使用固定身份算法版本 `v22_evidence_identity_v1`、来源类型、快照 UUID、规范化的逻辑定位信息、规范化标量及其类型。定位信息包含存在的竞品、指标单位/维度、query、地区/设备等区分项。

- 先以现有模型规则处理字符串/URL；不把所有业务文本改成小写，不对数字做近似舍入。bool、整数、浮点、字符串、null 在身份中明确区分。
- 对象键排序；语义集合如维度映射先检查重复键，再按键排序；真正有顺序含义的内容不重排。
- 不使用进程内 hash、随机数、当前时间、report ID、遍历下标或错误文案作为身份输入。
- 同一快照、同一定位和规范化值，在重复运行或改变适配器遍历顺序时得到相同 ID。不同快照，即使值相同，也必须得到不同 ID。
- 输入快照是不可变对象；把其内部数组改序却仍声称原快照和原校验和有效，应拒绝。这不属于“遍历顺序改变”的稳定性保证。
- 同 ID 且全部证据字段一致时合并，并合并排序后的来源路径；同 ID 但原始值、采集时间、健康状态或其他证据字段冲突时，报错而不是后写覆盖先写。

所有来源缺口、限制和 trace 均确定性排序，避免依赖适配器调用顺序。改动身份算法须独立提升内部算法版本并更新回归样例，不改变冻结报告结构。

## 8. 健康、置信度与覆盖缺口

### 8.1 观察资格

第一方数值证据要求 health 为 healthy、身份匹配为 matched，且在固定 `evaluated_at` 时未过期。未满足资格的第一方来源不输出业务指标证据，输出实际来源状态的覆盖记录。不得仅凭存在 snapshot UUID 就宣称 verified 或 Full Evidence Coverage。

公开来源中，成功检查到的页面/记录可形成证据；部分失败不抹除其他成功观察，但必须保留失败和采样限制。未成功检查的页面、缺席的资料和未返回的评论不能产生内容证据。

公开成功观察的 health_status 为 healthy；失败记录按实际来源状态映射为 error 或 unavailable。partial 和 empty 是覆盖原因，不是新增 HealthStatus 枚举；成功返回空列表可具有 healthy 的来源状态，但只能支持“本次结果为空”的覆盖证据。身份不匹配保持真实来源健康状态，另外记录身份缺口，不能混同为网络失败。

置信度使用固定保守映射：通过资格校验的第一方测量为 high；公开来源实际观察为 medium；覆盖状态证据为 low。这里的置信度只表达本次证据的使用等级，不把网页/评论的陈述认证为现实事实。

`evaluated_at` 是调用方固定输入，不默认读取当前时钟。相同快照、相同评估时点重复构建应得到相同结果；换评估时点导致过期资格改变是明确允许的变化。

所有来源均适用已有的 expires_at：在 `expires_at <= evaluated_at` 时只输出过期覆盖记录，不输出业务观察；没有声明过期时间时不擅自编造有效期。获取时间晚于评估时点属于上下文非法。prospect 模式不接收第一方快照；这项隔离与既有报告合同一致。

### 8.2 两类覆盖缺口

1. 有真实快照：状态异常、空结果或采样限制生成 `source_type=coverage` 的 Evidence，引用该快照与状态字段，normalized value 使用固定原因码，附来源健康和限制说明；不能从这些记录推导不存在的业务数值。
2. 完全没有快照：只生成内部 `coverage_gaps`，snapshot_id 为缺省；不生成要求非空 UUID 的 EvidenceItem。若后续要让 Finding 引用“未授权”等状态，需由持久化层先保存真实状态快照后再索引，本轮不代替该层造记录。

若调用方提交了实际载荷却没有必需绑定，按绑定错误拒绝，而不是偷偷降级为“完全没有快照”。

缺口至少区分 no_snapshot、not_connected、unavailable、empty、partial、unhealthy、identity_mismatch、identity_unconfirmed、expired。无快照时，只有调用方明确提供未连接状态才使用 not_connected；不能仅靠缺少数据猜测授权状态。

第一方真实零值不等于 empty；有 rows 或 aggregates 且存在指标时按实际内容处理。公共搜索成功但返回零条时记录“本次搜索返回为空”，不推断“市场中没有竞争对手”。

来源限制去重、排序。单条 Evidence 超过合同 20 项限制时保留前 19 项及固定的额外限制提示，完整限制保留在 source_summaries；不静默丢失覆盖说明。

## 9. 错误、安全与资源边界

内部确定性错误使用固定代码与安全说明，不返回源载荷、客户查询全文、评论全文或访问凭据：

- `V22_EVIDENCE_SOURCE_INVALID`：载荷格式、标量、日期或定位信息非法。
- `V22_EVIDENCE_SNAPSHOT_BINDING_INVALID`：缺少必需绑定、归属不符或同 UUID 绑定冲突。
- `V22_EVIDENCE_CHECKSUM_MISMATCH`：载荷与声明的校验和不符。
- `V22_EVIDENCE_ID_CONFLICT`：同 ID 的证据字段不一致。
- `V22_EVIDENCE_LIMIT_EXCEEDED`：超过构建资源上限。

来源校验失败必须使本次构建整体失败，不返回看似完整的部分成功索引。正常的业务数据缺口通过第 8 节表达，不与篡改/错绑混为一谈。

仅提取上述白名单字段，不导出原始 HTML、整段 provider 响应、token、Cookie、请求头或未列入范围的用户字段。错误日志只含代码及必要的非敏感来源标识。公开评论按已有快照内容和限制使用，不新增采集或延长留存期限。

内部构建参数默认最多 50,000 条唯一 Evidence、序列化后的完整结果最多 20,000,000 字节；超过即明确失败，不默默截断证据集合。参数可在本地测试中降低，不新增 API 参数；沿用各采集器既有页面、结果和评论上限。片段提取限额按第 6.1 节披露，不与整个索引超限处理混淆。

## 10. 测试与验收

### 10.1 核心身份测试

- 同一 fixture 重复运行、来源输入顺序改变及对象键顺序改变时，输出和 ID 稳定。
- 不同 snapshot、source、query、坐标、device、competitor、metric/unit/dimensions 或规范化值不能误合并。
- 完全重复观察去重并保留全部来源路径；证据冲突、绑定冲突明确失败。
- bool/int/float/string/null 区分，有限零值保留；非法日期、非有限数字、未知字段及错绑载荷拒绝。

### 10.2 适配器与来源测试

- 站点结构页、深度页、旧版片段复用、受限片段披露、失败/禁止抓取页面。
- SERP 三种结果类型、多个查询和同名不同地点、空结果与部分失败，不能串用来源。
- 三个确认竞品的页面、公开资料、评论及回复，缺失来源和竞品身份冲突。
- GSC/GBP/GA4 行指标、汇总指标、维度、单位、资源身份、覆盖日期、真实零值；重复维度键拒绝。
- 未授权/缺少快照、空 payload、不健康、身份未确认/不匹配、固定时点过期，均无伪造指标或快照。
- tablet 等现有合同无法直接展示的上下文被完整保留和披露，不错误转换。

### 10.3 合同、边界与回归

- 每条生成 Evidence 都通过冻结 `EvidenceItem` 模型；trace 引用真实输出 ID，物理来源或稳定选择器可解析回绑定快照。
- 构建前后输入深拷贝一致；测试以无网络的 fixture 为唯一数据源。
- 超限、校验和篡改、安全错误信息、限制条目溢出均有回归测试。
- 后端完整 pytest、前端现有合同测试/类型检查、冻结合同和 V22-030 辅助资源漂移检查通过；不靠修改冻结 fixture 消除失败。
- 在前端测试中对离线构建产出的 Evidence 使用现有 Schema 的 EvidenceItem 定义验证，测试样例后端存放于 `tests/fixtures/report_v22_evidence/`，前端对应 `src/lib/report-v22/test-fixtures/evidence/`。两端内容以确定性生成与哈希检查约束，不改 V22-030 的 validation 资源目录或冻结合同树；不填造 Findings/Actions 来冒充完整报告。

本轮验收是“真实形状的已绑定 fixture 可确定性生成可追溯证据”，不是生产快照持久化、完整报告或线上授权联调已完成。
