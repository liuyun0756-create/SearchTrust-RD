# SearchTrust v2.2 公共 Findings 检查点阶段设计

日期：2026-09-02

状态：用户已批准完整书面设计；尚未开始业务代码实施。

范围：把现有完整公共数据 Findings 构建能力封装为可校验、可恢复、可重试的正式任务阶段，作为后续 Prospect 生产执行器的稳定组成部分。

主要仓库：SearchTrust-RD。本轮不修改 search-trust 前端运行时。

## 1. 目标与已确认范围

本轮采用方案 A，实现独立的 `CheckpointedPublicFindingsStage`。它统一处理已经采集并绑定的以下公共证据：

- 网站库存、页面事实与站内业务信息；
- SERP 市场结果；
- 已确认竞争对手及其公共资料；
- 客户公开 GBP 及其与网站信息的对齐结果。

阶段输出继续使用现有 `PublicFindingsResult`，包含完整证据索引、Findings、逐规则检查状态、网站整体汇总和页面类型汇总。

本轮不实现：

- 三条行动建议；
- Dify 文案生成；
- 最终 `ReportV22` 组装；
- 完整 Prospect 生产执行器；
- GSC、授权 GBP、GA4 等第一方 verified execution；
- 前端页面、接口开放、生产开关启用、部署或发布。

## 2. 现状与方案选择

当前代码已经具备：

- 纯函数入口 `build_public_findings(PublicFindingsInput | dict) -> PublicFindingsResult`；
- 网站、市场、竞争对手和 GBP 公共规则；
- 网站与 GBP 名称、地址、电话、服务区域的确定性对齐；
- `JobCheckpoints.run_once` 提供的任务内原子首次写入与恢复能力；
- 网站库存、SERP 市场及竞争对手采集阶段可参考的检查点模式。

比较过三种实现路径：

1. 新建独立、版本化的公共 Findings 检查点阶段，内部复用现有纯构建器。该方案边界清楚，后续完整 Prospect 执行器可以直接编排调用，用户已选择此方案。
2. 在 Worker 中直接调用 Findings 构建器。代码较少，但把任务编排、持久化和业务规则耦合在一起，后续扩展会返工。
3. 立即建设通用 DAG/工作流引擎。扩展性较强，但超出本轮需求和风险边界。

## 3. 阶段接口与模块边界

新增模块：

- `app/jobs_v22/public_findings_stage.py`

核心入口为：

```python
class CheckpointedPublicFindingsStage:
    async def build(
        self,
        *,
        job_id: UUID,
        request: PublicFindingsInput,
        checkpoints: JobCheckpoints,
    ) -> PublicFindingsResult: ...
```

阶段只负责：

1. 严格重验输入模型；
2. 生成稳定输入摘要和版本化检查点键；
3. 命中时校验并恢复检查点；
4. 未命中时调用现有 `build_public_findings`；
5. 校验并原子保存标准结果；
6. 把业务构建错误映射为稳定的 v2.2 任务错误。

阶段不负责采集网站、SERP、竞争对手或 GBP，不读取网络、文件、数据库、环境变量或当前时钟，不生成报告文案，也不改写任何业务规则。

`build_public_findings` 继续是 Findings 业务事实的唯一构建入口。新阶段不复制、不分叉其中的判断逻辑。

## 4. 数据流

完整执行顺序固定：

1. 接收 `job_id`、`PublicFindingsInput` 和当前任务的 `JobCheckpoints`。
2. 将输入重新校验为严格模型，拒绝额外字段、非法类型、非有限数值和无效嵌套引用。
3. 使用标准 JSON 计算 `input_digest`。摘要输入包含完整的、会影响输出的已校验请求，并显式绑定阶段版本和规则集版本。
4. 构造检查点键：`v22_public_findings_stage_v1:result:<digest>`。
5. 若检查点存在，按第 5 节校验封装、绑定和结果后直接返回。
6. 若检查点不存在，调用 `build_public_findings(validated_input)`。
7. 重新校验 `PublicFindingsResult`，计算结果校验和，并构建检查点封装。
8. 通过 `JobCheckpoints.run_once`/首次写入机制保存。并发执行时，先成功写入的值是标准结果；其他执行读取并校验该值。
9. 返回持久化的标准 `PublicFindingsResult`。

本阶段保持独立，不替换当前 `UnavailableV22Executor`。后续实现完整方案 B 时，由 Prospect 执行器显式调用本阶段。

## 5. 检查点合同与验证

检查点封装使用严格模型，字段为：

- `schema_version = "public_findings_checkpoint_v1"`；
- `job_id`；
- `input_digest`；
- `ruleset_version = "v22_public_findings_v1"`；
- `result_checksum`；
- `result: PublicFindingsResult`。

读取检查点时必须全部满足：

- 封装结构和嵌套结果通过严格模型校验；
- `job_id` 与当前任务相同；
- `input_digest` 与当前标准输入相同；
- 阶段版本及规则版本与当前代码期望相同；
- `result.ruleset_version` 与封装一致；
- 重新计算的结果校验和等于 `result_checksum`；
- 完整结果仍满足现有引用、ID、数量和字节限制。

任一条件失败均视为检查点损坏或错误绑定。阶段不能静默接受、覆盖或退回旧值。

输入摘要只保证“同一标准化请求”稳定命中。会影响业务含义的数组顺序或字段变化必须产生不同摘要；不能为了提高命中率而擅自重排有语义顺序的数据。

## 6. 业务缺失语义

阶段保留已经批准并实现的 Findings 业务语义，不把缺数据一律当成程序错误：

- 网站有值、GBP 无值：不匹配并生成对应 Finding；
- GBP 有值、网站无值：不匹配并生成对应 Finding；
- 两侧来源均合资格、必要内容均成功检查，但两侧都没有必要字段：生成错误级 Finding；
- 两侧有值时继续区分完全匹配、语义匹配、服务区域部分匹配和不匹配；
- 上游来源未采集、失效、身份不合资格、必要网站内容未完成检查或比较器无法可靠判断：规则为 `not_checked` 并保留固定原因，不能伪造成“字段缺失”或“不匹配”。

“两侧都没有”与“上游没有完成采集”必须严格区分：前者是完成检查后的业务问题，后者是未知状态。

## 7. 错误分类

本阶段的计算不访问外部服务，因此没有自身产生的网络型临时错误。

以下错误转换为稳定、不可重试的 `DeterministicJobError`：

- 输入模型或 Prospect 公共范围无效；
- 证据校验和错误；
- 来源、案件、快照或证据引用绑定错误；
- Finding/Evidence ID 冲突；
- Findings、规则评估或结果字节超过限制；
- 检查点结构损坏、版本不符、摘要不符、任务绑定不符或结果校验和不符。

错误代码保留 v2.2 和公共 Findings 阶段命名空间，并把底层已知错误映射为固定代码。用户消息必须安全且稳定，不能包含网页正文、地址、电话、供应商原始响应或内部异常堆栈。

未预期的编程错误不伪装成业务 `not_checked`；它继续进入现有 Worker 的失败处理和可观测链路。

## 8. 并发、幂等与日志

- 同一 `job_id` 和同一标准输入重复执行，返回同一标准检查点结果。
- 同一任务输入发生真实变化时使用新检查点，不能误用旧结果。
- 两个执行同时未命中时允许重复进行无副作用的纯计算，但只有首次成功写入的检查点成为标准值；双方最终返回同一标准结果。
- 阶段不得写入业务数据库或调用外部供应商，因此并发重复计算不会产生外部副作用或额外供应商费用。
- 日志仅记录阶段名、任务 ID、版本、摘要后缀、命中状态、结果计数和安全错误代码。
- 日志不得记录原始网页内容、证据原文、商家地址、电话、GBP 字段或完整请求。

## 9. 测试设计

新增阶段单元测试至少覆盖：

1. 首次执行生成完整结果并保存正确封装。
2. 相同任务和输入再次执行命中检查点，不再调用构建器。
3. 输入变化生成新键且不复用旧检查点。
4. 并发首次执行最终读取同一标准结果。
5. 错 schema_version、job_id、input_digest、ruleset_version、result_checksum 和非法嵌套结果分别稳定失败。
6. 已知 `FindingsError` 分类正确映射为不可重试任务错误。
7. 未知程序错误不被吞掉或改写为业务缺失。
8. 输出超过现有限制时拒绝保存。
9. 日志不泄露已知敏感样例值。

公共 Findings 回归测试继续覆盖：

- 网站、SERP、竞争对手、GBP 四类规则都进入结果；
- 完全匹配、语义匹配、部分匹配、不匹配；
- 网站单侧缺失、GBP 单侧缺失、成功检查后的两侧缺失；
- 来源未采集或不合资格时的 `not_checked`；
- Findings、评估、Evidence、roll-up 的确定排序和引用完整性；
- 数量、采样和字节限制。

验证顺序为：新增阶段测试、相关公共 Findings 测试、后端完整测试集。基线以实施开始时仓库实际测试数为准，不把旧的 1261 项数量写成硬编码门槛；要求全部通过且无现有回归。

## 10. 完成标准

满足以下条件即视为方案 A 完成：

- 存在可被其他编排器直接调用的 `CheckpointedPublicFindingsStage`；
- 它能从完整 `PublicFindingsInput` 构建并返回 `PublicFindingsResult`；
- 首次执行持久化严格、版本化、带输入绑定和结果校验和的检查点；
- 重试与并发执行恢复同一标准结果；
- 损坏或错误绑定的检查点明确失败；
- 业务缺失、未知状态和系统错误保持清晰区分；
- 网站、SERP、竞争对手和 GBP 的现有规则与测试不回退；
- 前端、API、主执行器和生产开关保持不变；
- 后续完整方案 B 只需编排调用本阶段，无须重写方案 A。

## 11. 实施顺序

设计批准后，实施计划按以下顺序展开：

1. 先以失败测试锁定检查点封装、键、恢复、损坏拒绝和错误映射。
2. 实现严格检查点模型与 `CheckpointedPublicFindingsStage`。
3. 补齐并发、敏感日志和资源边界测试。
4. 运行相关测试与完整后端测试集。
5. 记录完成文档；不开启功能开关，不部署。
