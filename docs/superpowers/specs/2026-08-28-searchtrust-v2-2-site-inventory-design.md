# SearchTrust v2.2 全站库存设计

日期：2026-08-28

里程碑：V22-021

状态：已确认，待实施

## 1. 目标

实现 SearchTrust v2.2 的全站库存采集能力：在后台持久任务中安全发现最多 500 个站内 URL，对库存页执行轻量结构检查，并从中确定性选择最多 50 个重点页进行深度内容采集。

该里程碑只生成可追溯的内部站点库存快照和冻结的 `SiteInventorySummary` 映射，不产生 Finding、评分、Top Action、诊断文案或完整报告结论。

## 2. 已确认范围

### 2.1 包含

- 站点根地址、主机范围和每跳重定向安全校验；
- `robots.txt` 读取与访问规则执行；
- `robots.txt` 声明的 sitemap、常见 `/sitemap.xml`、sitemap index、站内链接和 Firecrawl Map 的组合发现；
- URL 规范化、去重、过滤和最多 500 URL 的硬上限；
- 对库存页执行有界结构检查；
- 固定页面类型分类；
- 公开模式下按业务相关性和类型覆盖选择重点页；
- 验证模式下接受标准化 GSC 页面信号并提高相应页面优先级；
- 最多 50 个重点页的有界深度内容采集；
- 分阶段、分批次检查点和中断恢复；
- 内部库存快照、覆盖限制及冻结报告摘要映射；
- 确定性的固定测试和全量回归验证。

### 2.2 不包含

- 新增公开同步 API；
- 启用当前仍由 `UnavailableV22Executor` 保护的完整 v2.2 分析管线；
- SERP 市场采集和竞品发现，这些属于 V22-022 和 V22-023；
- 实际 GSC 授权、刷新、拉取或健康度判断连接器，这些属于后续第一方数据里程碑；
- PageSpeed、GBP、GA4 或竞品页面采集；
- v2.2 Evidence Ledger 的正式证据 ID 铸造，这属于 V22-031；
- 复用或修改 v2.1 的大型单页报告抓取流程；
- JavaScript 浏览器渲染、页面资源下载或站外递归抓取。

## 3. 技术方向

采用独立的原生受控采集器，Firecrawl 只作为补充发现来源：

1. 原生读取 robots 和 sitemap；
2. 原生执行同站 HTML 结构检查并扩展站内链接；
3. 原生完成规范化、分类和重点页选择；
4. 原生来源用尽且库存仍未达到 500 时，最多调用一次 Firecrawl Map；
5. 使用 `JobCheckpoints` 持久化每个阶段和批次的规范化结果。

V22-021 可以复用 V22-020 已验证的 URL 解析、公共地址检查和 DNS 固定连接边界，但使用独立的 `app/collectors/site_inventory.py` 领域模块。不得把同步预检抓取扩展为长时间全站任务，也不得调用 v2.1 的完整抓取与报告管线。

选择该方向的原因是它能同时控制 SSRF 风险、单站负载、供应商成本、结果稳定性和断点恢复。Firecrawl-first 会扩大外部依赖与结果波动；sitemap-only 则无法覆盖没有完整 sitemap 的站点。

## 4. 架构和数据流

全站库存作为后台分析任务中的独立阶段运行：

1. **站点入口确认**：规范化请求站点，验证首页和最终主机，获取 robots 规则；
2. **URL 发现**：依次合并 sitemap、站内链接和可选 Firecrawl 结果，生成最多 500 个规范 URL；
3. **结构检查**：分批获取库存 URL，记录状态、页面结构、链接和分类依据；
4. **重点页选择**：按业务相关性、页面类型覆盖和可选 GSC 信号排序；
5. **深度采集**：为最多 50 个重点页获取有界完整 HTML 和可分析文本，失败时继续补位；
6. **快照封装**：生成版本化内部快照，并映射为冻结 `SiteInventorySummary`。

V22-021 交付可被未来真实 `V22JobExecutor` 调用的阶段适配器，但不替换生产 `UnavailableV22Executor`，也不更改 `V22_ANALYZE_ENABLED` 的安全默认值。完整执行器只有在后续采集、证据、规则和报告阶段均完成后才能启用。

## 5. 内部数据合同

实现使用严格、版本化且拒绝额外字段的内部模型。模型名称可以在实施时按项目约定细化，但必须覆盖以下语义。

### 5.1 `SiteInventorySnapshot`

- `schema_version`：固定为库存快照版本；
- `root_url`、`canonical_host`、`started_at`、`completed_at`；
- `discovery_limit`、`deep_analysis_limit`；
- `pages`：最多 500 个 `InventoryPageRecord`；
- `deep_pages`：最多 50 个最终重点页记录；
- `deep_attempts`：重点页成功、失败与补位审计；
- `page_type_counts`；
- `source_counts`；
- `limitations`；
- 可选的 GSC 优先级输入摘要，不保存授权凭据或完整原始响应。

### 5.2 `InventoryPageRecord`

- 原始 URL、规范 URL、发现来源和最小发现深度；
- HTTP 状态、最终 URL、内容类型、读取字节数和检查状态；
- title、H1、canonical、meta robots 和结构化数据类型；
- 规范化站内链接；
- 页面类型、分类信号和确定性选择分数；
- 标准化错误类别，不保存内部堆栈或任意上游错误正文。

网络请求完成且取得受限、可解析的 HTML 时计为结构检查成功；HTTP 状态本身仍按原值记录。DNS、连接、超时、非 HTML、超限或解析失败保留页面记录，但不增加 `structurally_checked_count`。只有安全、允许访问且成功取得 HTML 的页面可进入深度候选池。

### 5.3 `DeepPageSnapshot`

- 规范 URL、最终 URL、页面类型和发现深度；
- 抓取时间、HTTP 状态、内容校验摘要；
- 有界 HTML、提取文本和关键结构字段；
- 选择原因、选择分数、是否成功深度分析；
- 标准化失败类别和限制。

内部模型保留失败尝试。冻结 `selected_pages` 表示最终选择结果，可以包含在候选耗尽后仍失败的页面；`deep_analyzed_count` 必须严格等于其中 `deep_analyzed=true` 的数量，并且不得超过结构检查成功数量。

## 6. URL 发现

### 6.1 来源顺序

发现按以下顺序运行：

1. `robots.txt` 中声明的 sitemap；
2. 常见 `/sitemap.xml`，以及有限深度和数量的 sitemap index；
3. 首页和已完成结构检查页面中的同站链接，采用有界广度优先；
4. 原生来源用尽且库存少于 500 时，最多一次 Firecrawl Map。

每个来源的结果在进入队列前立即规范化、过滤和去重。达到请求的 `generation_limits.max_site_urls` 或系统硬上限 500 后停止扩展。输入限制小于 500 时以较小值为准。

Firecrawl 通过 V22 独立适配器调用。不得直接复用会触发 v2.1 后续页面分析的流程；不得因重试已完成检查点而重复调用。并发重复执行的互斥仍由现有任务租约负责，检查点提供至少一次执行下的规范结果复用，而不声称跨并发进程的供应商绝对 exactly-once。

### 6.2 robots 语义

- 使用明确的 SearchTrust 库存 User-Agent；
- 优先匹配该 User-Agent，没有专属组时匹配 `*`；
- 被禁止的 URL 不发起页面请求；
- robots 返回 404/410 视为没有规则；
- robots 超时、5xx、响应超限或无法解析时记录限制，并只继续采集已知公开主站页面；
- robots 中声明的 crawl delay 在不超过系统上限的前提下执行；过大或不支持的值转为安全频率并记录限制；
- sitemap 中出现被 robots 禁止的 URL 时不绕过规则。

### 6.3 sitemap 边界

- 只接受 XML sitemap 和 gzip sitemap 的受限解压；
- 限制 sitemap index 深度、子 sitemap 数、压缩前后字节数和 XML 节点数量；
- 禁止外部实体和网络实体解析；
- sitemap 自身以及每个子 sitemap URL 都执行相同的主机和 SSRF 校验；
- 非法条目、站外条目和不支持格式被忽略并形成计数型限制，不中止其他来源。

## 7. URL 规范化与过滤

### 7.1 主机范围

- 只允许最初确认的主机，以及其严格对应的 `www`/非 `www` 形式；
- 首次安全首页重定向可以确定最终主机身份；
- 不自动扩展到其他子域名；
- canonical 或页面链接只有落在允许主机范围内才能参与去重和发现；
- 每次 DNS 解析、连接和重定向都执行公共地址校验与固定连接，禁止 DNS rebinding。

### 7.2 规范化规则

- 只允许 HTTP(S)，主机名小写并使用标准 IDNA；
- 移除用户信息、片段和默认端口；
- 统一空路径、默认首页和尾斜杠表达；
- 删除常见广告追踪、会话和分享参数；
- 查询参数按稳定顺序处理；仅保留被允许且可能改变公开正文的参数；
- 使用页面内合法 canonical 合并重复页面，但 canonical 不得越过允许主机或安全边界；
- 规范 URL 作为去重键，原始来源 URL 仅用于审计。

### 7.3 排除规则

- 登录、注册、账户、购物车、结账和管理路径；
- 站内搜索、排序、筛选、日历翻页和无限组合参数；
- 邮件、电话、JavaScript、data、blob 等非 HTTP(S) 链接；
- 图片、字体、脚本、样式、音视频、压缩包、可执行文件和其他静态资源；
- 明显的退出、删除、提交或其他带副作用路径；
- 外部域名和未批准子域名。

过滤器必须基于稳定规则和测试夹具，不得使用模型猜测 URL 是否安全。

## 8. 结构检查与页面分类

### 8.1 有界结构检查

结构检查使用 GET 而不是 HEAD，以避免不支持 HEAD 的站点产生虚假失败。默认限制为：

- 同站并发请求最多 10；
- 同站发起频率最多每秒 5 次，robots 更严格时服从更低频率；
- 独立连接、读取和总超时；
- 最多读取 256 KB HTML；
- 每跳重定向重新验证 URL、DNS 和允许主机；
- 不执行 JavaScript，不获取图片、脚本、CSS 或 iframe；
- 不自动提交表单，不携带站点 Cookie 或用户凭据。

系统配置可以降低并发、频率和字节上限；提高配置不得超过代码定义的安全硬上限。

### 8.2 固定页面类型

页面类型固定为：

1. `home`；
2. `service_index`；
3. `service_detail`；
4. `service_area`；
5. `location`；
6. `about`；
7. `contact`；
8. `team`；
9. `review_testimonial`；
10. `case_study_portfolio`；
11. `faq`；
12. `blog_index`；
13. `blog_post`；
14. `product_category`；
15. `product_detail`；
16. `legal`；
17. `other`。

分类按以下优先级执行：明确结构化数据与页面标记、规范路径规则、title/H1 文本信号、链接关系。分类规则必须是纯函数；相同输入必须得到相同标签和理由。无法可靠分类时使用 `other`，不得为了覆盖统计而强行猜测。

`page_type_counts` 统计成功完成结构检查的页面，并按固定页面类型顺序输出；零计数类型可以省略，但同一实现中必须保持一致。

## 9. 重点页选择与深度采集

### 9.1 候选与配额

重点页上限取请求 `generation_limits.max_deep_pages` 与系统硬上限 50 的较小值。选择分两层进行：

1. 首页，以及与 `primary_service`、`target_market` 明确匹配的服务页和地区页优先；
2. 在剩余名额中保证服务、地区、品牌介绍、联系、团队、评价、案例和 FAQ 等业务类型的代表性；
3. 博客文章和产品详情使用类型上限，避免单一高数量类型占满重点页；
4. 剩余名额按确定性综合分数补齐；
5. 分数相同时按规范 URL 排序。

类型配额是覆盖目标而不是伪造名额：站点没有某类页面时不产生占位记录。

### 9.2 GSC 页面优先级

验证模式接受可选的标准化 `GscPagePriority` 输入，至少包含规范 URL、impressions、clicks 和采样时间。适配器只消费已被上游判定为健康、未过期且属于当前允许主机的数据。

GSC 信号提高同类页面内的优先级，但不能取消首页、核心业务匹配和类型覆盖。V22-021 不连接 Google、不刷新令牌、不解释原始 GSC 响应；没有合格 GSC 输入时自动使用公开模式，不降低任务成功状态。

### 9.3 深度采集与补位

- 每个重点页最多读取 2 MB HTML；
- 使用与结构检查相同的网络安全、主机、robots、频率和跳转边界；
- 优先复用结构检查已取得的字节，只有需要剩余正文时才继续有界获取；
- 成功后保存提取文本和关键结构，不下载页面资源；
- 失败页面保留尝试记录，并选择下一名合格候选补位；
- 直到成功数量达到上限、候选耗尽或任务预算耗尽；
- 候选耗尽时允许少于 50 个成功页面，并写入限制，不伪造成功。

## 10. 检查点与恢复

库存阶段使用带版本的稳定检查点键，至少包括：

- 站点入口与 robots 结果；
- 各发现来源的规范化结果；
- 分批结构检查结果；
- 最终页面分类与选择顺序；
- 每个重点页的深度采集结果；
- 完整库存快照。

检查点值必须是可由严格内部模型重新验证的 JSON，不保存不可序列化客户端对象。批次键包含稳定输入摘要；实现或合同语义变化时提升检查点版本，禁止把旧结构误当成新结果。

重启或任务重试时先验证既有检查点，再跳过已完成阶段。坏检查点不得静默使用：应记录稳定错误并根据阶段决定安全重算或确定性失败。现有任务租约、取消语义和终态幂等规则保持不变。

## 11. 失败和降级语义

以下情况使库存阶段确定性失败：

- 根 URL 不安全或跳转离开允许安全边界；
- 首页无法安全访问；
- 最终没有任何成功完成结构检查的可用页面；
- 内部快照无法通过严格模型或冻结计数约束。

以下情况记录限制并继续：

- robots、某个 sitemap 或 Firecrawl 单项不可用；
- sitemap 含坏条目、外部 URL 或被禁止 URL；
- 个别库存页超时、超限、非 HTML 或返回不可解析内容；
- 重点页失败后补位，或候选耗尽导致不足 50 页；
- 达到 500 URL 上限，无法证明已覆盖站点剩余页面；
- 没有健康 GSC 输入，只能使用公开模式选择。

稳定内部错误类别至少区分不安全目标、根站不可达、robots 不可用、sitemap 不可用、页面超时、响应超限、非 HTML、解析失败、Firecrawl 不可用、候选耗尽和空库存。上游原始错误不得直接进入面向用户的摘要。

## 12. 冻结报告映射

库存快照映射到 `app.report_v22.models.SiteInventorySummary`：

- `discovered_url_count`：内部 `pages` 中规范 URL 数量，最多 500；
- `structurally_checked_count`：成功完成结构检查的页面数量；
- `deep_analyzed_count`：最终 `selected_pages` 中 `deep_analyzed=true` 的数量，最多 50；
- `discovery_limit`：实际应用的请求限制，最多 500；
- `deep_analysis_limit`：实际应用的请求限制，最多 50；
- `page_type_counts`：成功结构检查页面的固定分类计数；
- `selected_pages`：最多 50 个最终重点页的 URL、页面类型、发现深度和深度状态；
- `limitations`：确定性、可面向报告的覆盖限制。

V22-031 完成前，V22-021 不自行发明正式 evidence ID。映射器接受后续证据索引提供的 URL 到 evidence ID 关联；没有关联时使用冻结字段允许的空列表。

映射后必须再次通过冻结 Pydantic 模型验证，尤其保证：

- `structurally_checked_count <= discovered_url_count`；
- `deep_analyzed_count <= structurally_checked_count`；
- `deep_analyzed_count` 等于 `selected_pages` 中成功标记数量；
- `selected_pages` 不超过 50。

## 13. 配置和成本边界

新增库存专用配置，建议使用 `V22_SITE_INVENTORY_` 前缀，至少覆盖：

- 结构并发和每秒请求数；
- 连接、读取和总超时；
- 结构检查与深度采集最大响应字节；
- 最大重定向次数；
- sitemap index 深度、文件数和解压限制；
- 结构检查批次大小；
- Firecrawl Map 是否可用及单次结果上限。

生产默认值为结构并发 10、每秒 5 次、结构 HTML 256 KB、深度 HTML 2 MB、发现 500、深度 50。请求只能在冻结 `GenerationLimits` 范围内降低 500/50 上限，不能提高系统硬上限。

单个库存任务最多调用一次 Firecrawl Map。所有测试默认使用固定适配器，不访问真实外网或消耗供应商额度。

## 14. 可观测性与隐私

结构化日志只记录：

- `job_id`、库存快照版本和规范化域名；
- 当前阶段、批次号、队列数和成功/失败计数；
- 来源计数、页面类型计数和限制码；
- 分阶段耗时、重试状态和标准化提供商状态；
- URL 的安全摘要或哈希，而不是包含查询参数的完整原始 URL。

日志不得记录完整页面正文、完整 HTML、Cookie、Authorization、Google OAuth 信息、供应商密钥、原始供应商响应或内部堆栈。页面正文只存在于受任务生命周期约束的库存快照中，并由后续持久化里程碑定义长期保留策略。

## 15. 测试策略

### 15.1 单元测试

- URL 规范化、`www` 范围、IDNA、默认端口、尾斜杠和参数处理；
- 登录、购物车、搜索筛选、静态资源和危险动作过滤；
- robots 专属组、通用组、禁止规则、404 和暂时失败；
- sitemap、sitemap index、gzip、坏 XML、外部实体和解压上限；
- 页面结构提取、canonical 合并和站内链接；
- 17 类页面分类、`other` 回退和固定顺序；
- 类型配额、业务匹配、GSC 加权、分数并列和失败补位；
- 500/50 以及请求较低限制；
- 冻结摘要计数不变量和 evidence ID 空关联。

### 15.2 安全与集成测试

- IPv4、IPv6、localhost、云元数据、私网和混合 DNS 结果；
- DNS 固定连接与 rebinding 防护；
- 每跳重定向、跨主机 canonical 和子域名拒绝；
- robots/sitemap/页面的超时、超限、非 HTML 和压缩炸弹；
- 结构检查并发与频率上限；
- Firecrawl 只在原生发现不足时调用且每任务最多一次；
- 不下载子资源、不提交表单、不携带站点会话。

### 15.3 持久任务测试

- 发现、结构批次、选择、深度页和终态快照的恢复；
- 已完成检查点不重复执行；
- 坏检查点的验证和处理；
- worker 中断、租约重试和最终快照幂等；
- 生产 `UnavailableV22Executor` 保持不变。

### 15.4 验证

- V22-021 新增单元、集成和任务恢复测试；
- v2 冻结合同导出检查；
- Python 编译检查；
- 后端全量测试；
- 工作区差异和生产安全开关检查。

## 16. 验收标准

- 无 sitemap 的安全网站仍可通过站内链接形成库存；
- 大型网站严格截断在请求限制和 500 硬上限，并声明未检查范围；
- 重复 URL、canonical 和追踪参数不会重复计数；
- 全部可用库存页得到结构检查，最多 50 个重点页得到有界深度采集；
- 公开模式保持类型覆盖，验证模式能稳定使用合格 GSC 页面信号提高优先级；
- 单个页面或单个发现来源失败不会无故终止整个库存；
- 重试可从持久检查点恢复，不重复已完成批次；
- 输出严格满足 `SiteInventorySummary` 的 500/50 和计数约束；
- v2.1 路径和测试保持不变；
- 完整 v2.2 执行器和生产分析入口仍保持关闭。
