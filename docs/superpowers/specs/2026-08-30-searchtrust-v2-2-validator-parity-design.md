# SearchTrust v2.2 模型与校验器一致性设计

日期：2026-08-30

范围：V22-030

状态：沿用现有合同、补齐双端校验的方向已确认；本书面设计待用户审核，尚未实施。

适用仓库：后端 `SearchTrust-RD`、同级前端 `search-trust`。

## 1. 目标与边界

V22-003 已建立 Pydantic 模型、JSON Schema、TypeScript 类型和两个共享合法报告样例。本阶段复用这些产物，补齐已有后端语义规则在前端的缺口，修复前端的错误拒绝，并建立共享回归样例。

本阶段不新增报告字段，不修改 `2.2.0` 合同版本、Schema、原始合法 fixtures 或合同 manifest，不手改生成的 TypeScript 类型。后端现有模型的接受规则作为本轮语义校验的基准，不为迁就前端而放宽规则。

不实现 V22-031 证据索引、Finding/Action 生成、报告 UI、生产采集或部署。不修改 API 请求语义、v2.1 和 PDF 路径。不启用 `V22_ANALYZE_ENABLED`、`V22_COMPETITOR_DISCOVERY_ENABLED`，保留生产 `UnavailableV22Executor`。

## 3. 方案选择

采用现有 Pydantic 单一事实源、AJV 结构校验加 TypeScript 语义校验的方式，增加共享的正反例测试。

- 相比重建一套 Schema/类型生成体系，保留现有消费者和冻结产物，变更范围更小。
- 相比仅修重复查询，覆盖已经复现的其他缺口，并用两端共享样例约束后续维护。
- 不引入独立合同服务、跨语言运行时依赖或新的通用校验框架。

## 4. 校验分层与职责

### 4.1 结构层保持不变

后端继续使用严格 Pydantic 模型；前端继续使用 AJV 2020 与既有格式校验。保留 `coerceTypes: false`、`removeAdditional: false`、`useDefaults: false`，未知字段仍应拒绝。

结构校验成功后才执行语义校验。校验器不得补造数据、删除未知字段或改写传入报告；成功时返回原报告。

### 4.2 补齐已有语义规则

1. 查询：3–5 项由 Schema 保证；语义层拒绝空白和按后端规范化规则等价的重复项。比较两处查询数组时保留数组顺序。
2. 覆盖日期：检查全部 Evidence 及 GSC、GBP、GA4 envelope。只有两端日期均存在时检查开始不晚于结束；相等或单端缺省保持合法。
3. 站点统计：结构检查数不得超过发现数，深度分析数不得超过结构检查数，深度分析数必须等于 `selected_pages` 中真值标记之和。缺省页面列表按空列表参与此项比较。
4. 路线图：阶段必须依次为 `days_1_30`、`days_31_60`、`days_61_90`，继续检查已有行动引用规则。
5. 目标地区：按已定义字段比较，不依赖对象键顺序；仅对模型中默认值为 null 的可选字段，将缺省与 null 视为等价。必填字段仍必须存在，实际值不一致仍拒绝。
6. 竞品唯一性：继续检查唯一 ID 和后端规范化后的完整网址，覆盖根路径尾斜杠、主机大小写和默认端口等价形式。不改成只按域名去重，不自行删除有意义的路径或查询参数。

查询大小写比较必须对应 Python `casefold()`，不能用简单 `toLowerCase()` 替代。字符串去首尾空白也应与后端本轮使用的规则一致。采用后端运行环境生成、记录 Unicode 版本的字符规范化辅助表，供前端比较函数使用；该表独立于冻结合同产物，生成内容需要可重现并有漂移检查。只在相关语义比较的局部副本上使用，不对报告整体做隐式转换。

前端的辅助比较逻辑按查询、目标地区、网址划分为小函数；不引入通用对象归一化器，不让无关字段继承缺省/null 等价规则。

### 4.3 保留现有规则，不增加业务约束

现有 ID 唯一性、引用完整性、三项行动顺序、步骤顺序、八层顺序、版本差异、第一方快照与完整覆盖规则保持原义并纳入回归测试。

本轮不新增行动依赖环检测、引用列表去重、页面数量与可配置上限的新关系等双方目前未实现的约束；这些会改变后端可接受数据范围，需另行明确需求。

本轮的一致性承诺针对现有语义规则及共享样例，不宣称 Pydantic 与 AJV 对任意原始 JSON 的所有格式、强制转换或默认行为完全等价。若实施中发现其他影响当前语义规则的差异，应先补复现样例并核对基准；需要变更冻结合同或后端接受规则时暂停该项并说明。

## 5. 共享回归样例与同步

### 5.1 单一维护源

共享回归资源在后端维护于 `tests/fixtures/report_v22_validation/`，同步到前端 `src/lib/report-v22/test-fixtures/validation/`，不写入两端冻结的 `contracts` 目录。

资源包括：

- `cases.json`：稳定样例 ID、基础 fixture 名称、变更操作、预期接受/拒绝；拒绝样例附前端错误代码与相关字段路径。
- 资源 manifest：测试资源内容哈希、字符规范化辅助表哈希及所依赖的两个基础 fixture 的哈希。它不是合同 manifest，也不写入报告正文。

字符规范化辅助表包含生成内容与 Unicode 版本元数据，单独存放于后端 `app/report_v22/normalization_data.json`，同步到前端 `src/lib/report-v22/generated/normalization-data.json`。运行时只引用这份生成数据，不依赖测试样例或测试加载器；它与已有 `generated/types.ts` 分开维护。

基础报告仍引用既有 prospect/verified fixture，不复制整份报告到每个反例，也不维护两份独立的预期结果。

### 5.2 样例变更规则

测试加载器每次深拷贝基础 fixture，只支持三种明确操作：设置字段、删除字段、重排对象键。路径由字段名/数组下标组成，不执行表达式或任意代码。

设置操作的父路径必须存在；允许添加最后一级字段，以测试未知字段拒绝。删除目标必须存在；重排键必须恰好覆盖原对象全部键。未知操作、非法路径、重复样例 ID 或不存在的基础 fixture 均导致测试失败，不静默跳过。

Python 测试使用 `model_validate_json`，避免严格 Python 对象入口对日期/UUID 的不同要求；TypeScript 测试调用公开的 `validateReportV22`。两端必须消费全部样例并核对相同接受结果；不要求不同校验库的完整错误文本或错误数量一致。

### 5.3 同步与漂移检查

新增独立校验辅助资源同步/检查脚本，显式指定前端目录。写入只限上述测试资源目录及两个明确命名的字符规范化数据文件，不整体替换 `generated` 或 `app/report_v22` 目录；`--check` 仅比较字节内容和 manifest，不写文件。单仓库测试可独立运行，联调时额外检查两个仓库资源一致。

保留既有合同导出器与 `--check --frontend-dir` 的行为和输出。不能通过更新冻结 Schema 或合法 fixture 来隐藏本次校验差异。

## 6. 错误与安全边界

- 结构错误继续返回 `REPORT_CONTRACT_INVALID`。
- 语义错误继续返回 `REPORT_REFERENCE_INVALID`，不新增公开错误代码。
- 新增错误提供具体字段路径和固定规则说明，不回显查询全文、网址、快照内容等输入值。
- 成功和失败均不得改变原始输入，新增深拷贝前后对比测试。
- 校验、同步与测试不联网，不依赖真实客户数据、外部服务密钥或运行中的生产服务。

## 7. 验收标准

1. 第 2 节全部已复现差异转为共享回归样例，两端结果符合预期。
2. 补齐正向边界：唯一 Unicode 查询、3/5 项查询、零页面、计数相等、日期相等/缺省、正常路线图、对象键重排、地区可选字段缺省；真正不同的地区和查询顺序仍拒绝。
3. GSC、GBP、GA4 分别覆盖日期错误；prospect 和 verified 均有合法基线及各自的类型条件反例。
4. 已有 ID、引用、行动、八层、版本差异及第一方规则都有共享样例覆盖；测试不能因加载器静默跳过而假通过。
5. 字符规范化覆盖普通大小写、`Straße`/`STRASSE`、希腊 sigma 及不应合并的字符，记录生成表的运行环境版本；网址比较覆盖已约定等价形式与不同路径的对照样例。
6. 后端合同测试及完整回归、前端合同测试和类型检查通过。任何无关环境阻塞单独记录，不宣称未执行的验证已通过。
7. 原合同导出、前后端同步和 TypeScript 类型生成无漂移；新增测试资源及辅助表的检查通过；冻结产物字节不变。
8. 仅使用本地测试数据，生产开关与执行器不变，不推送或部署。
