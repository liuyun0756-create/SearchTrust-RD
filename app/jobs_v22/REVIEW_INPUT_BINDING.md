# Review generation input binding

`ReviewInputRepository.freeze` persists a `ReviewGenerationInput` prepared by the owner-scoped `ReviewGenerationPreparer`. It requires an existing, active, reserved Verified task. The separate default-off review intake now creates the task, reservation and input atomically; this repository remains the internal storage boundary.

The RPC locks the Case, job and reservation, checks the current run generation/deadline, and independently matches the selected immutable source records. One job can bind one input. A duplicate submission recovers the original freeze time; another input conflicts. It does not reserve or consume credits.

`resolve` returns the original input under current owner/Case/job checks. `expected_checksum` pins a known task request; omit it only when recovering an unknown write outcome by the same known task identity. Resolution never selects a later decision revision or updates evidence dates. A new run generation can read the same input while an older run is refused.

The returned `FrozenReviewGeneration` has a process-local provenance seal. Pass it to `CheckpointedReviewGenerationStage.build_frozen` with matching job/generation and generation-fenced `JobCheckpoints`. Copies, fabricated instances, mutated nested values and generation mismatches do not retain authorization. This seal is a handoff integrity check, not a substitute for the future completion transaction rechecking job state and entitlement.

Transport failures or unverifiable success receipts mean the save may have committed. Recover the same task; do not create a replacement job, refund, or recompute a new preparation time automatically.

Migration `20261027120000_bind_v22_review_generation_input.sql` introduces no intake/debit RPC. The newer `20261027150000_start_v22_review_generation.sql` adds the atomic job/reservation/binding transaction behind a separate default-off entry. Migration `20261027130000_settle_v22_review_reports.sql` adds formal 2.2.3 persistence and atomic completion over that binding. Generic success without its matching formal report remains blocked. Pure content candidates remain `requires_delivery_review`, and the old completed-report path continues to reject them.

Use `ReviewCompletionService` to construct the formal report from a trusted frozen input and persist it through `ReviewReportRepository`. Completion consumes the existing reservation without a second debit. After an unknown outcome, `read` recovers a completed report and replays it against the saved full input; an identical completion request returns an idempotent receipt even after the original deadline.

The frontend now has a dedicated, default-off owner review/approval workspace and safe PDF/pinned-share delivery for completed 2.2.3 reports. Migration `20261027140000_review_report_delivery.sql` adds immutable delivery requests/revisions and owner-scoped retrieval; it does not create generation tasks or change credits. The default-off `review-generation` owner BFF/internal API and SQL-leased `review_worker` now connect atomic task/reservation/input creation, durable dispatch and completion. The worker uses its own ARQ function and database status, so new review reports never enter legacy result parsing or callbacks. Continuous 2.2.3 rounds now use `review_plan_basis` and migration `20261028090000_continue_v22_multi_round_reviews.sql`: a bounded plan/diagnosis projection keeps its own digest and the complete source-report digest separately. New evidence/generation preparation requires `V22_MULTI_ROUND_REVIEWS_ENABLED`; previously frozen tasks can still finish through their pinned input. Authorized real-account acceptance and release remain pending.
